As AI systems move into production, architecture increasingly extends beyond components and interfaces into data, evaluation, models, agents, security and operational behaviour.

AI systems are changing the shape of software architecture.

There is a temptation to interpret this as the end of traditional architecture: models write code, agents connect systems, and increasingly capable AI handles work that previously required carefully designed application logic.

I think the opposite is closer to reality.

AI does not remove architecture. It moves some of the architectural questions to places where we have historically had less certainty.

The component is no longer the whole system

Traditional application architecture gives us reasonably familiar boundaries. AI introduces components whose behaviour is partly probabilistic. An LLM is not simply another service with a deterministic contract.

The same request can produce different outputs. A model can change underneath an application. An agent may decide to call a tool differently from what we expected. Retrieval can return different context as the underlying data changes.

That makes some architectural assumptions less reliable. It does not make architecture less important.

Evaluation becomes part of architecture

For AI systems, correctness can be less binary. We may need to ask whether an answer is grounded, whether the model follows the intended policy, whether the agent selects the right tool, what happens when the model is uncertain, and what a successful interaction costs.

Those questions affect system boundaries, observability, deployment strategy, data architecture and operational processes.

Data becomes an architectural boundary

AI can make data far more accessible. That is both a strength and a risk.

A useful architecture distinguishes between what the model can technically access and what the system should allow it to access. Data permissions, retrieval boundaries, identity, tenancy and auditability become part of the architecture.

Agents make the boundary less obvious

An agent can turn a simple interaction into a sequence of actions:

User → Model → Planner → Retrieval → Tool → External system → Result → Model → User

Every additional decision point introduces another place where the system can behave unexpectedly. Architecture therefore has to answer which actions require approval, which tools are read-only, what the maximum scope of an action is, how failed actions recover, and how decisions can be reproduced.

These are architecture questions.

Where architecture matters more

The useful question is not whether AI will make architects obsolete. It is which decisions become more important as systems become less deterministic.

Increasingly, I think those decisions are about boundaries: around data, authority, automation, failure, cost, and what we allow a system to decide for itself.

The more capable the system becomes, the more important those boundaries are.
